# Site-wide redesign — working contract

Updated 10 September 2026. This is the current execution plan, not a completion report.

## Direction

Explain ALPHAC before decorating it. The visitor should understand that Canli runs and studies its own strategies in paper execution, publishes inspectable evidence, and offers developer validation tools. Do not imply funded execution, independently audited results, or achieved performance targets.

Use the reference's clear subject, spatial continuity and editorial pacing, not its shipping assets. Our signature should be a readable research input moving through decision, paper execution and publication. Abstract glass is not a substitute for product explanation.

Palette: paper #F4F4F4, ink #111111, white #FFFFFF, cobalt #0016CB, copper #FF5500. Cobalt and ink carry readable text; copper is an accent, not small text on paper. Keep Chakra Petch display, Inter body, IBM Plex Mono data. Explanatory content uses light surfaces; dark scenes are deliberate punctuation. Native Blender output must match intended display resolution; never call an upscaled bitmap a native high-resolution render.

## Latest user direction — clarity without losing impact

The user reports repetition in the current result. Phase 3's passing checks are not visual acceptance. Keep the high-quality mechanism studies, real product views and cinematic continuity, while making each section's purpose clearer. Consistency means shared design rules, not identical layouts or the same explanation repeated throughout the site.

### Phase 4 approved implementation order

1. Map repetition before cutting: compare the main process, Evidence Core, rebalance and footer explanations; compare offering/API/access calls to action; compare paper-console figures with the dated evidence dashboard. Assign each unique fact, qualifier, control and link a retained destination. Preserve original URLs and deep links. Do not move material claim limitations out of sight just to shorten the page.
2. Give every homepage section one job: introduce ALPHAC; explain the strategies; show the actual paper record; explain the research-to-publication sequence once; demonstrate developer validation; offer research depth; disclose limits; identify accountability; resolve questions; offer an appropriate next action. Remove repeated framing, not evidence. Present the specific consolidation map in the phase review.
3. Design the navigation as a product component: clear labels and grouping for strategies/systems, research, developers and evidence; one deliberately chosen primary action; visible current-page state; predictable sticky behavior; readable status information without crowding. Validate final labels against real route destinations before implementing them.
4. Cover every navigation state in editable Figma and the browser: desktop resting/scrolled/menu-open, narrow desktop, mobile closed/open, nested destinations, keyboard focus, Escape/return focus and reduced motion. No hover-only routes, trapped focus, header-obscured anchors, horizontal overflow or content jumps. Include Safari and startup-shift investigation.
5. Apply the shared shell to subpages through its source/generators. Verify representative developer/tool pages, strategy/performance/system hubs, research/methodology/evidence hubs and long articles/measurements/publications. A shared CSS change is not proof that every page has been reviewed.
6. Review the whole homepage flow, not isolated screenshots: alternate immersive product moments with readable evidence; avoid consecutive oversized headline-plus-paragraph layouts and repeated pinning. Retain the original high-resolution assets and source-bound product demonstrations. Motion must explain relationships and preserve readability, keyboard access and reduced-motion alternatives.

### Subpages are explicit deliverables

- Phase 4 establishes and tests the shared shell across page families; it does not complete their unique content designs.
- Phase 5 covers the developer landing page, API onboarding/docs and every calculator/tool, including input, error, loading and result states using mocked external writes.
- Phase 6 redesigns strategy, performance, systems, methodology, research and evidence hubs around their distinct user tasks, without cloning the homepage's promotional structure.
- Phase 7 covers every remaining inventoried article, measurement, publication, trial, note and route. Maintain separate changed, visually reviewed and functionally verified states for each route; protect original publication documents.
- Phase 8 verifies navigation between these families, source/link preservation, representative visual states and all-route checks. No blanket “production ready” claim before this evidence exists.

Acceptance requires clarity and visual impact together: a new visitor can identify what runs today, its paper-execution boundary, what glassbox exposes, what developers can do, and where to inspect the supporting record. Repetition may be removed only with an explicit content-preservation map; no invented performance, omitted caveats or silently dropped pages. Continue asking permission before each phase. Phases 1–13 were explicitly approved. Phase 13 local corrections are verified; Figma sync and user visual approval remain pending. Production promotion remains separate.

## Homepage content decisions

- Keep strategies, paper record, API access, research and claim limitations in the main reading path.
- The expanded evidence room repeats the opening process through offering, core, films and rebalance explanations. Initially close this existing disclosure instead of deleting unique descriptions, data hooks or evidence links. Deep links must still reveal their targets.
- Keep the dated evidence dashboard expanded: limitations must not become harder to find while simplifying marketing content.
- Next review candidates: merge introductory offering copy into the opening; choose one principal process illustration; shorten the repeated footer story. These are proposals, not implemented deletions.
- Preserve published documents and URLs. A redundant marketing section is not a redundant research record.

## Anti-loop and evidence rules

1. One bounded batch at a time: inspect, implement, capture, critique, test, record outcome.
2. Track inventoried, changed, visually reviewed and functionally verified separately. Never infer visual quality from a passing build.
3. After each batch, compare with the reference and this brief. If two revisions fail for the same reason, change the approach instead of adding effects.
4. Preserve the existing content baseline. Do not regenerate it to conceal losses. Record intentional copy changes separately.
5. Generated pages must be changed through their source generator. Preserve unrelated user/Claude edits.
6. Screenshots must correspond to the current build/origin. Do not run a build while a browser audit is capturing the dev server.
7. No claims of production readiness until batch 8 is evidenced. Deployment and marketing are separate steps.
8. Obtain explicit permission before every phase. Phases 1–14 were approved; the updated isolated preview is deployed with Figma sync pending. The next phase requires approval. Do not repeat test issuance or create additional synthetic records without a concrete need and approval. Production promotion and user visual approval remain separate from automated verification. This document does not control background goal scheduling or promise unattended work.
