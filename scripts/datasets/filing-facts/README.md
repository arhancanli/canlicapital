# Filing facts: financial reasoning items verified from SEC XBRL data

Generated by `report.mjs` from the build and evaluation records; do not edit the figures by hand.

Each item is a question about one company's SEC filings whose answer is computed from the company's
XBRL facts (US public domain) and re-derived by an independent checker (`check.mjs`). Every item
cites the accession number and SEC folder of each filing it depends on.

## Templates

| template | asks for | hops |
|---|---|---|
| lookup | one value as reported in a named annual filing | 1 |
| change | the percent change of one concept between two fiscal years or balance dates | 2 |
| ratio | a ratio of two concepts for the same period (margin, leverage, cash share) | 2 |
| net_assets | total assets minus total liabilities at one balance date | 2 |
| unanswerable | a period before the concept's earliest annual XBRL fact; the right answer is that the XBRL filings do not report it | 1 |

Rules: only annual-report facts (fiscal period FY on 10-K, 20-F, 40-F and their amendments), so a
question never mixes a quarter with a year; one value per concept, period end and unit; a period
whose annual filings disagree on the value is dropped as ambiguous; an unanswerable item claims
absence only from the company's XBRL filings.

## The v0 build

- 1,882 items from 402 companies (a stratified sample of active filers across the CIK range of the live company release).
- By template: change 402, lookup 402, net_assets 338, ratio 402, unanswerable 338.
- The independent checker accepted every item in this build. While the generator was written it rejected items citing periods whose filings disagree, which is how the ambiguity rule above was found.

## Baseline: gpt-5.4-mini, 150 items (30 per template, fixed seed)

| | closed book | with canli-validation-mcp's company tool |
|---|---|---|
| accuracy, all items | 19.3% | 68.0% |
| accuracy on answerable items | 0.8% | 65.8% |
| numbers given on answerable items that were wrong | 98.7% (76 numbers) | 17.7% (96 numbers) |
| answerable items the model called "not reported" | 36.7% | 14.2% |
| unanswerable items answered "not reported" | 93.3% | 76.7% |
| unanswerable items answered with an invented number | 0.0% | 0.0% |
| mean tokens per item | 187 | 3,833 |

By template (accuracy): change 0.0% closed / 40.0% with the tool; lookup 0.0% closed / 80.0% with the tool; net_assets 0.0% closed / 73.3% with the tool; ratio 3.3% closed / 70.0% with the tool; unanswerable 93.3% closed / 76.7% with the tool.

Accuracy on all items rewards a model that answers "not reported" to everything, because the
unanswerable items then score. The behaviour rows separate knowing that data is absent from
declining to answer. Where the model with the tool was wrong, the misses checked by hand during
development were the model's arithmetic or row reading, not the tool's data: the tool returned the
item's exact cited facts.

Historical v0 run records used legacy answer parsing and preserve parsed answers and scores,
but no raw model responses, so their original scores cannot be independently rescored. The
effect of the parsing changes on the old baseline is unmeasured. The v1 runner retains raw
answers, source bindings and a scoring version; see [EVALUATION.md](./EVALUATION.md) for offline
replay and v1 coverage, denominator and abstention rules. Historical files remain unchanged.

## v1 (2026-10-07): restatements and a fresh split

v1 adds two kinds of question a model cannot answer from memory, generated by `generate-v1.mjs`
(`generate.mjs` stays byte-identical because every v0 run record binds its bytes):

- **restatement** (`restatements.mjs`): the first-reported value of a figure that a later annual
  filing revised. A tool that only knows each figure's latest value answers with the revision and is
  wrong; a point-in-time tool is right. Built from the raw SEC companyfacts snapshot each record names
  (every filing of every fact, with period start dates). USD amounts from annual reports only: per-share
  figures and share counts change with stock splits without being restated, and a duration counts only
  when both filings give the same start date. `checkRestatement` re-derives each item from the snapshot
  by a separate path (the cited first fact must be the earliest annual filing of that period).
- **fresh split** (`--filed-after`): only facts filed after a date, so a model whose training data ends
  before it cannot have seen the answers. A comparative year re-reported in a newer annual report
  carries that report's filing date, so year-over-year questions still have two periods.

Release in `public/datasets/filing-facts/v1/` (CC BY 4.0, `SHA256SUMS`):

| file | items | contents |
|---|---|---|
| `filing-facts-v1-all.jsonl` | 2,243 | 402 companies; v0's templates plus 361 restatement items; 0 rejected by the checker |
| `filing-facts-v1-fresh.jsonl` | 241 | facts filed after 2026-04-01; 15 restatement items; the checker rejected 32 generated "unanswerable" items whose period had in fact been reported before the cutoff |

Sources: `fetch-sources.mjs` downloads each company record and its raw snapshot from canlicapital.com and
checks the snapshot against the sha256 the record names. Reproduce with
`node scripts/datasets/filing-facts/generate-v1.mjs <sources> out.jsonl [--filed-after 2026-04-01]`
(seed 20261007, 5 items per company plus at most one restatement item). As with v0, expected answers
are machine-derived and checked by an independent program; no item is human-verified yet.

## Human layer

- `ANNOTATION_GUIDELINES.md`: how an annotator checks an item against the filing itself.
- `gold-packet.mjs` writes a stratified gold packet (50 items in v0); two annotators fill copies independently.
- `agreement.mjs a.json b.json gold.json` reports agreement on complete pairs, missing labels and total gold coverage. Duplicate IDs, invalid labels and changed source items are refused.
- `adjudicate.mjs` exports only items with two distinct named complete submissions and a third reviewer's explicit filing-backed decision. Review identities/qualifications remain self-declared until independently checked. No item is called human-verified until a human has verified it; none has yet.

## Release

The v0 items and run records are published under CC BY 4.0 in `public/datasets/filing-facts/v0/`,
with the dataset card at https://canlicapital.com/research/filing-facts-v0. Anyone can regenerate
items from the public company data with `generate.mjs`. Restatement items (first-reported versus
later-reported values) need the raw SEC snapshots each record points to, and are planned for v1.
